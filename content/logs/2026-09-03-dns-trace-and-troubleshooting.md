오늘은 브라우저에 도메인을 입력한 뒤 웹 페이지가 열리기까지의 과정에서 **DNS가 담당하는 범위와 담당하지 않는 범위**를 구분했다. 결론부터 말하면 DNS는 도메인을 IP 주소 등의 정보로 해석하지만, 해당 서버의 포트를 열거나 웹 애플리케이션을 실행해 주지는 않는다.

재사용할 수 있는 개념 설명은 [[DNS는 어떻게 동작할까?]]에 정리되어 있다. 이번 기록은 질문에 답하면서 이해한 순서와 장애 진단 관점을 남긴다.

## `dig`와 `dig +trace`의 차이

일반적인 `dig` 명령은 현재 사용 중인 재귀 DNS 리졸버에 최종 답을 요청한다.

```bash
dig example.com A
```

반면 `dig +trace`는 루트 DNS부터 시작해 위임 경로를 따라간다.

```bash
dig +trace example.com
```

두 명령의 질문은 다음처럼 구분할 수 있다.

- `dig`: 최종 답이 무엇인가?
- `dig +trace`: 그 답을 어떤 위임 경로를 거쳐 찾는가?

조회 경로를 단순화하면 다음과 같다.

```text
루트 DNS
  → .com TLD DNS
  → example.com 권한 DNS
  → 최종 A 또는 AAAA 레코드
```

루트 DNS는 `.com`을 담당하는 TLD DNS를 안내한다. TLD DNS는 `example.com`을 담당하는 권한 DNS를 안내한다. 실제 도메인의 최종 레코드는 권한 DNS가 제공한다. 따라서 특정 도메인의 위임이 어느 단계에서 끊어졌는지 확인하려면 `dig +trace`가 유용하다.

## 최종 응답 서버와 최종 정보 제공자는 다르다

일반 `dig` 결과의 `SERVER` 항목에는 보통 내 질의에 응답한 **재귀 DNS 리졸버**가 표시된다.

```text
내 컴퓨터
  → 재귀 DNS 리졸버
      → 루트 DNS
      → TLD DNS
      → 권한 DNS
  ← 최종 응답
```

권한 DNS가 최종 레코드를 가지고 있더라도, 내 컴퓨터는 재귀 리졸버에 조회를 맡기고 그 리졸버로부터 답을 받는다. 즉, 최종 정보를 가진 서버와 사용자에게 직접 응답한 서버를 구분해야 한다.

## TTL이 남아 있으면 전체 경로를 다시 조회하지 않는다

DNS 응답에는 캐시할 수 있는 시간을 나타내는 TTL(Time To Live)이 포함된다. 브라우저, 운영체제 또는 재귀 리졸버의 캐시에 유효한 응답이 있다면 루트부터 권한 DNS까지의 전체 경로를 다시 조회하지 않아도 된다.

```text
첫 조회: 캐시 없음 → 전체 조회 → 응답 저장
재조회: 유효한 캐시 있음 → 저장된 응답 사용
TTL 만료: 캐시 무효 → 다시 조회
```

이 특성은 DNS 조회를 빠르게 만들지만, 서버 IP를 변경할 때는 주의해야 한다. 이전 IP가 담긴 응답의 TTL이 아직 만료되지 않은 사용자는 계속 기존 서버로 접속할 수 있다.

안전하게 서버를 이전하려면 일반적으로 다음 순서를 고려한다.

1. 변경 전 기존 TTL만큼 여유를 두고 TTL을 낮춘다.
2. DNS 레코드를 새 IP로 변경한다.
3. 이전 서버를 일정 시간 함께 유지한다.
4. 이전 캐시가 만료된 뒤 기존 서버를 종료한다.

DNS를 변경하는 순간에만 TTL을 낮추면 이미 캐시된 응답에는 변경 전 TTL이 남아 있을 수 있다. 그래서 TTL 조정은 실제 변경보다 미리 이루어져야 한다.

## DNS 성공과 웹 접속 성공은 같은 뜻이 아니다

`dig`가 올바른 새 IP를 반환해도 HTTPS 접속은 실패할 수 있다. 이 경우 DNS 레코드를 계속 바꾸기보다 DNS 다음 단계를 확인해야 한다.

```text
DNS로 IP 확인
  → 네트워크 경로와 라우팅
  → TCP 443번 포트 연결
  → TLS 협상과 인증서 검증
  → HTTP 요청
  → 웹 서버 응답
```

가정용 공유기 뒤의 서버라면 NAT와 포트 포워딩도 이 경로에 포함된다. 공개 DNS의 `A` 레코드에 IP를 등록하는 것만으로 내부 서버의 443번 포트가 자동으로 외부에 공개되지는 않는다.

## 연결 오류 메시지로 다음 확인 지점 좁히기

HTTPS 연결 실패를 조사할 때 `curl`의 상세 출력을 이용하면 어느 단계에서 실패했는지 확인하는 데 도움이 된다.

```bash
curl -v https://example.com
```

`Connection refused`는 보통 대상 장비까지 도달했지만 해당 포트에서 연결을 받지 않는다는 뜻이다. 다음 가능성을 먼저 살펴본다.

- 웹 서버 프로세스가 실행 중인지
- 프로세스가 443번 포트에서 수신 중인지
- 방화벽이 연결을 명시적으로 거부하는지

반면 `Connection timed out`은 응답이 돌아오지 않았다는 뜻이므로 방화벽의 패킷 차단, 라우팅 또는 포트 포워딩 문제를 함께 확인해야 한다. 오류 메시지만으로 원인을 확정할 수는 없지만, 조사 순서를 좁힐 수는 있다.

서버에서는 DNS 레코드보다 먼저 열린 포트와 수신 프로세스를 확인한다. 그다음 네트워크 정책과 TLS 설정을 차례로 점검한다.

## 오늘 이해한 진단 순서

오늘의 핵심은 **DNS 장애와 DNS 이후의 연결 장애를 분리하는 것**이었다.

1. `dig`로 도메인이 기대한 IP를 반환하는지 확인한다.
2. 위임 문제가 의심되면 `dig +trace`로 루트, TLD, 권한 DNS의 경로를 확인한다.
3. 이전 IP가 보이면 레코드와 TTL, 캐시 상태를 확인한다.
4. 올바른 IP가 보이면 열린 포트, 서버 프로세스, 방화벽과 포트 포워딩을 확인한다.
5. TCP 연결 뒤에 실패하면 TLS 인증서와 웹 서버 설정을 확인한다.

DNS는 인터넷의 주소 안내소와 비슷하다. 목적지 주소를 알려 주지만 목적지까지 가는 길, 출입문, 그 안에서 동작하는 서비스까지 보장하지는 않는다. 이 경계를 이해하면 접속 실패 때 같은 DNS 레코드만 반복해서 수정하는 대신 실패한 구간을 순서대로 좁힐 수 있다.
