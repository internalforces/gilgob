## 오늘의 질문

QUIC은 [[TCP와 UDP는 무엇이 다를까?|UDP]] 위에서 동작하면서 어떻게 신뢰성 있는 웹 통신을 제공하고, HTTP/3는 이를 이용해 무엇을 개선할까?

> [!question] 핵심질문
> UDP는 전달 순서와 손실 복구를 보장하지 않는데, QUIC은 왜 TCP 대신 UDP를 기반으로 선택했을까?

## 한 문장으로 이해하기

**QUIC은 기존 인터넷 장비가 널리 지원하는 UDP를 운반 기반으로 사용하되, 신뢰성·암호화·혼잡 제어·독립 스트림을 직접 제공하는 전송 프로토콜이며, HTTP/3는 QUIC 위에서 동작하는 HTTP다.**

```text
HTTP/3      웹 요청과 응답의 의미와 형식
   ↓
QUIC        연결, 암호화, 손실 복구, 스트림, 혼잡 제어
   ↓
UDP         QUIC 패킷을 데이터그램으로 운반
   ↓
IP          목적지 호스트까지 패킷 전달
```

## QUIC은 무엇일까?

QUIC은 UDP 기반의 다중화되고 안전한 전송 프로토콜이다. 애플리케이션에는 흐름 제어되는 여러 스트림, 낮은 지연의 연결 설정, 네트워크 경로가 바뀔 때 연결을 이어 갈 수 있는 기능을 제공한다.

UDP 자체는 데이터그램의 도착, 순서, 재전송, 혼잡 제어를 보장하지 않는다. QUIC은 이 기능들을 UDP에 맡기지 않고 QUIC 프로토콜 안에서 구현한다.

```text
UDP:  데이터그램을 보낸다
QUIC: 패킷 번호와 ACK로 손실을 감지한다
      필요한 정보를 새 패킷으로 다시 보낸다
      스트림 안의 데이터를 순서대로 전달한다
      전송량을 조절한다
      TLS를 이용해 통신을 보호한다
```

따라서 “UDP가 QUIC에 신뢰성을 제공한다”가 아니라 **“QUIC이 UDP 위에 신뢰성을 구현한다”**가 정확하다.

## 왜 UDP 위에 만들었을까?

새로운 전송 프로토콜을 IP 위에 바로 추가하면 운영체제, NAT, 방화벽 같은 중간 장비가 이를 알지 못해 차단하거나 잘못 처리할 수 있다. UDP는 이미 널리 배포되어 있으므로 QUIC을 UDP 데이터그램 안에 담으면 기존 네트워크 기반을 통과하기 쉽다.

또한 QUIC은 운영체제 커널에만 의존하지 않고 사용자 공간의 라이브러리나 애플리케이션으로 구현할 수 있다. TCP 커널 구현이나 중간 장비 전체가 바뀌기를 기다리지 않고 새 버전과 기능을 배포하기 유리하다.

UDP를 선택했다고 해서 모든 네트워크에서 QUIC이 반드시 동작하는 것은 아니다. UDP를 차단하는 방화벽이나 네트워크도 있으므로 HTTP/3 연결이 실패하면 클라이언트는 TCP 기반 HTTP로 대체할 수 있어야 한다.

## HTTP/3와 QUIC은 무엇이 다를까?

QUIC과 HTTP/3는 같은 프로토콜이 아니다.

| 구분 | QUIC | HTTP/3 |
| --- | --- | --- |
| 역할 | 데이터를 안전하고 신뢰성 있게 전달 | HTTP 요청과 응답을 표현 |
| 위치 | 전송 프로토콜 | 애플리케이션 프로토콜 |
| 주요 책임 | 연결, 암호화, 스트림, 손실 복구, 혼잡 제어 | 메서드, 상태 코드, 헤더, 콘텐츠 |
| 관계 | 여러 애플리케이션 프로토콜이 사용할 수 있음 | QUIC을 전송 기반으로 사용 |

HTTP/3는 각 요청과 응답 쌍에 QUIC 스트림 하나를 사용한다. QUIC은 스트림별로 신뢰성 있는 순서 전달을 제공하고, 연결 전체에는 공통 혼잡 제어를 적용한다.

## 독립 스트림은 패킷 손실을 어떻게 다룰까?

HTTP/2도 하나의 연결에서 여러 HTTP 작업을 다중화하지만, 전송 기반인 TCP에는 하나의 순서 있는 바이트 스트림만 보인다. TCP 패킷 하나가 손실되면 해당 바이트가 복구될 때까지 그 뒤에 도착한 데이터도 애플리케이션에 전달할 수 없다. 이 때문에 손실과 직접 관계없는 HTTP 작업도 함께 대기할 수 있다.

HTTP/3의 QUIC 연결은 여러 독립 스트림을 전송 계층에서 구분한다.

```text
하나의 QUIC 연결
├─ 스트림 A: HTML ───────────────▶ 계속 진행
├─ 스트림 B: CSS  ── 패킷 손실 ──▶ B만 복구 대기
└─ 스트림 C: 이미지 ─────────────▶ 계속 진행
```

스트림 B의 데이터가 손실되면 B 안에서는 순서를 맞추기 위해 복구를 기다려야 하지만, A와 C는 계속 진행할 수 있다. 이 구조는 TCP 전송 계층의 HOL(Head-of-Line) 블로킹이 모든 HTTP 작업으로 퍼지는 문제를 줄인다.

> [!note] 스트림이 완전히 서로 무관한 것은 아니다
> QUIC은 연결 전체에서 혼잡 제어를 공유한다. 네트워크가 혼잡하면 여러 스트림의 전송 속도가 함께 영향을 받을 수 있다. 독립 스트림이 제거하는 것은 주로 한 스트림의 순서 복구가 다른 스트림의 전달까지 직접 막는 현상이다.

## 연결 설정 시간은 어떻게 줄일까?

TCP 기반 HTTPS는 일반적으로 먼저 [[TCP 3-way handshake|TCP 연결]]을 만들고, 그 위에서 TLS 보안 설정을 수행한 뒤 HTTP 데이터를 교환한다.

```text
TCP 기반 HTTPS 새 연결
TCP 연결 설정 → TLS 보안 설정 → HTTP 요청

HTTP/3 새 연결
QUIC 연결 설정 + TLS 보안 설정 → HTTP 요청
```

QUIC은 TLS 1.3을 전송 프로토콜에 통합한다. 패킷 손실이 없는 새 연결은 보통 한 번의 왕복인 1-RTT 안에 연결과 보안 설정을 완료할 수 있다.

이전에 연결했던 서버라면 클라이언트가 저장된 정보를 이용해 첫 응답을 기다리기 전에 애플리케이션 데이터를 보내는 0-RTT도 사용할 수 있다. 그러나 0-RTT 데이터에는 공격자가 같은 요청을 다시 보내는 재전송 공격 위험이 있으므로, 중복 실행되면 문제가 되는 요청에는 주의해야 한다.

## 패킷이 손실되면 누가 복구할까?

UDP는 손실을 복구하지 않는다. QUIC 수신자는 받은 패킷 범위를 ACK로 알리고, 송신자는 이 정보와 타이머를 이용해 손실을 감지한다.

QUIC에서는 손실된 패킷 그 자체를 같은 번호로 다시 보내지 않는다. 손실된 패킷에 포함되었던 필요한 프레임 정보를 새로운 패킷에 담아 전송한다. 패킷 번호는 새 패킷마다 새로 부여된다.

```text
QUIC 패킷 10 전송 ──X 손실
QUIC 패킷 11 전송 ─── 도착
ACK를 바탕으로 10의 손실 감지
필요한 정보를 QUIC 패킷 12에 담아 전송
```

## 자주 하는 오해

### QUIC은 UDP이므로 신뢰성이 없다

QUIC의 기반인 UDP에는 신뢰성 기능이 없지만, QUIC 자체가 ACK, 손실 감지, 재전송, 흐름 제어, 혼잡 제어를 제공한다.

### QUIC이 UDP를 사용하는 이유는 UDP가 항상 빠르기 때문이다

UDP 사용만으로 성능이 보장되지는 않는다. QUIC이 UDP를 선택한 핵심 배포상의 이유는 기존 네트워크 기반과의 호환성과 사용자 공간 구현 가능성이다. 실제 성능은 지연, 손실, 서버와 클라이언트 구현, 네트워크 정책에 따라 달라진다.

### HTTP/3에서는 패킷 손실이 다른 요청에 전혀 영향을 주지 않는다

한 스트림의 순서 복구는 다른 스트림을 직접 막지 않지만, 연결 전체의 혼잡 제어와 네트워크 용량은 공유한다. 심한 손실과 혼잡은 연결의 여러 스트림에 영향을 줄 수 있다.

### QUIC은 HTTP/3에서만 사용한다

HTTP/3가 대표적인 QUIC 사용 사례지만, QUIC은 일반 목적 전송 프로토콜이다. 다른 애플리케이션 프로토콜도 기본 QUIC의 신뢰성 있는 스트림을 사용할 수 있다. 비신뢰성 애플리케이션 데이터그램이 필요하면 기본 기능이 아니라 별도로 협상하는 QUIC DATAGRAM 확장을 사용해야 한다.

## 핵심 정리

- QUIC은 UDP 위에서 동작하지만 신뢰성·암호화·혼잡 제어를 직접 제공한다.
- UDP를 사용하는 핵심 이유는 기존 인터넷 기반과의 호환성 및 배포 용이성이다.
- HTTP/3는 QUIC의 독립 스트림을 이용해 한 스트림의 손실이 다른 스트림까지 직접 막는 현상을 줄인다.
- QUIC은 연결과 TLS 설정을 결합해 새 연결의 준비 단계를 줄인다.
- UDP 차단, 공유 혼잡 제어, 0-RTT 재전송 위험처럼 적용할 때 고려할 한계도 있다.
