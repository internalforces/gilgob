## 오늘의 질문

브라우저에 `example.com`을 입력하면 컴퓨터는 어떻게 웹 서버의 주소를 알아낼까? 그리고 DNS 조회가 성공했는데도 웹 사이트에 접속하지 못하는 이유는 무엇일까?

> [!question] 핵심 질문
> DNS는 도메인을 외부에 공개하는 시스템일까, 아니면 도메인을 통신에 필요한 주소로 해석하는 시스템일까?

## 한 문장으로 이해하기

**DNS(Domain Name System)는 사람이 읽기 쉬운 도메인 이름을 컴퓨터가 통신할 때 사용할 IP 주소 등의 정보로 해석하는 분산 시스템이다.**

```text
example.com ── DNS 조회 ──▶ 192.0.2.10
   도메인                    IP 주소
```

DNS의 핵심 방향은 **도메인 → IP 주소**다. DNS 자체가 사설 IP를 공인 IP로 바꾸거나 서버의 포트를 열어 주는 것은 아니다.

## DNS 조회는 어떻게 진행될까?

브라우저는 먼저 가까운 캐시에 이미 알고 있는 답이 있는지 확인한다.

```text
브라우저 캐시
  → 운영체제 캐시
  → 재귀 DNS 리졸버
  → 권한 DNS 서버
```

앞단에서 유효한 답을 찾으면 뒤의 단계까지 가지 않는다. 이 때문에 한 번 방문한 도메인의 DNS 조회가 더 빨라질 수 있다.

캐시에 답이 없으면 내 컴퓨터는 보통 재귀 DNS 리졸버에 최종 답을 요청한다. 재귀 리졸버는 통신사가 제공하거나 `1.1.1.1`, `8.8.8.8`처럼 별도의 공개 서비스로 제공될 수 있다.

```text
내 컴퓨터
  │  "최종 IP까지 찾아줘"
  ▼
재귀 DNS 리졸버
  │
  ├─▶ 루트 DNS: ".com은 어디에 물어보면 돼?"
  ├─▶ .com TLD DNS: "example.com은 누가 관리해?"
  └─▶ 권한 DNS: "example.com의 IP는 뭐야?"
```

여기서 각 서버의 역할은 다음과 같다.

| 구성요소 | 역할 |
| --- | --- |
| 재귀 DNS 리졸버 | 사용자를 대신해 최종 답을 찾고 결과를 캐시한다. |
| 루트 DNS | `.com`, `.kr` 같은 TLD의 담당 서버를 안내한다. |
| TLD DNS | `example.com`을 담당하는 권한 DNS 서버를 안내한다. |
| 권한 DNS | 해당 도메인의 DNS 레코드를 가지고 최종 응답을 제공한다. |

내 컴퓨터가 리졸버에 “최종 답을 찾아 달라”고 요청하는 것은 **재귀 질의**다. 리졸버가 루트와 TLD DNS에서 다음에 물어볼 서버를 차례로 안내받는 과정은 **반복 질의**다.

## 주요 DNS 레코드

DNS는 IP 주소 외에도 도메인과 관련된 여러 정보를 레코드로 보관한다.

| 레코드 | 역할 | 예시 |
| --- | --- | --- |
| `A` | 도메인을 IPv4 주소에 연결한다. | `example.com → 192.0.2.10` |
| `AAAA` | 도메인을 IPv6 주소에 연결한다. | `example.com → 2001:db8::10` |
| `CNAME` | 하나의 도메인을 다른 도메인의 별칭으로 지정한다. | `www.example.com → example.com` |
| `NS` | 해당 도메인의 권한 DNS 서버를 지정한다. | `example.com → ns1.example.net` |
| `MX` | 이메일을 수신할 메일 서버를 지정한다. | `10 mail1.example.com` |
| `TXT` | 도메인 소유권 확인이나 메일 정책 등에 쓰이는 문자열을 저장한다. | `"service-verification=..."` |

`MX` 레코드의 우선순위 값은 작을수록 먼저 사용한다. `TXT` 레코드는 문자열을 실행하지 않는다. 메일 서버나 도메인 인증 서비스 같은 외부 시스템이 그 값을 읽고 의미를 해석한다.

### CNAME과 HTTP 리다이렉트는 다르다

`CNAME`은 DNS 단계의 별칭이다. `www.example.com`이 `example.com`의 `CNAME`이라면 브라우저는 최종 IP를 찾아 접속하지만 주소창에는 계속 `www.example.com`이 표시된다.

반면 HTTP 리다이렉트는 웹 서버가 브라우저에 다른 URL로 다시 요청하라고 알려 주는 응답이다. 이때는 주소창의 도메인도 바뀌 수 있다.

## TTL과 DNS 캐시

TTL(Time To Live)은 DNS 응답을 캐시할 수 있는 시간을 초 단위로 나타낸다.

```text
example.com.  300  IN  A  192.0.2.10
              └─ 300초 동안 캐시 가능
```

서버 IP를 바꿀 예정이라면 미리 TTL을 낮추어 이전 IP가 캐시에 오래 남지 않게 할 수 있다.

```text
TTL을 미리 낮춘다
  → DNS를 새 IP로 변경한다
  → 이전 서버도 잠시 유지한다
  → 이전 캐시가 만료된 뒤 기존 서버를 종료한다
```

변경 직후 이전 서버를 끄면 아직 이전 IP를 캐시한 사용자는 TTL이 만료될 때까지 접속하지 못할 수 있다. 이전 서버가 아직 살아 있다면 접속 실패 대신 잠시 기존 서버로 연결될 수 있다.

## DNS는 외부 접속을 만들지 않는다

DNS는 도메인을 IP로 해석할 뿐이다. 그 다음 접속에는 [[IP와 Port|IP와 포트]], 라우팅, NAT, 포트 포워딩, 방화벽, 서버 설정이 함께 관여한다.

```text
도메인 입력
  → DNS로 공인 IP 조회
  → 해당 IP의 443번 포트와 연결
  → TLS 협상
  → HTTP 요청
  → 웹 서버 응답
```

가정용 공유기 뒤의 서버를 외부에서 접속하려면 공개 DNS의 `A` 레코드에 사설 IP `192.168.1.10`을 입력하는 것으로는 부족하다.

```text
도메인
  → 공인 IP
  → 공유기의 포트 포워딩
  → 192.168.1.10 내부 서버
```

공인 IP가 자주 바뀌는 환경에서는 DDNS(Dynamic DNS)를 사용해 IP 변경을 감지하고 `A` 레코드를 자동으로 갱신할 수 있다. DNS 관리 업체가 바뀐 것이 아니므로 `NS` 레코드를 바꾸는 것은 아니다.

## dig로 DNS 상태 확인하기

`dig`로 레코드 유형별 응답을 확인할 수 있다.

```bash
dig example.com A       # IPv4
dig example.com AAAA    # IPv6
dig example.com NS      # 권한 DNS 서버
dig example.com MX      # 이메일 수신 서버
dig example.com TXT     # 문자열 레코드
```

응답에서 주의 깊게 볼 부분은 다음과 같다.

```text
;; ANSWER SECTION:
example.com.  300  IN  A  192.0.2.10

;; SERVER: 192.0.2.53#53
```

- `ANSWER SECTION`은 최종 DNS 응답을 보여 준다.
- 숫자 `300`은 남은 TTL이다.
- `SERVER`는 내 질의에 답한 DNS 서버다. 일반적인 조회에서는 보통 내 컴퓨터가 이용한 재귀 DNS 리졸버다.
- `#53`은 DNS가 사용하는 포트 번호를 나타낸다.

### 접속 실패를 어디서부터 확인할까?

| 확인 결과 | 먼저 볼 영역 |
| --- | --- |
| `dig` 결과가 이전 공인 IP다. | DNS 레코드와 TTL, 캐시를 확인한다. |
| `dig` 결과가 현재 공인 IP와 일치한다. | DNS 이후의 포트 포워딩, 방화벽, 서버 실행 상태를 확인한다. |
| IP는 맞지만 HTTPS 접속이 실패한다. | 443번 포트, TLS 인증서, 웹 서버 설정을 확인한다. |

DNS 결과가 이미 정확한 IP라면 `A` 레코드를 계속 바꾸기보다 DNS 이후의 연결 단계를 확인해야 한다.

## 자주 하는 오해

### DNS가 로컬 주소를 외부에 공개한다

DNS는 이름을 주소로 해석한다. 사설 IP를 인터넷에서 라우팅하거나 포트를 자동으로 공개하지 않는다.

### NS를 바꾸면 웹 서버 IP가 바뀐다

`NS`는 DNS 관리 주체를 지정하고 `A`는 IPv4 주소를 지정한다. 웹 서버만 이전한다면 보통 `A` 레코드를 바꾸고, DNS 관리 업체를 이전할 때 `NS`를 바꾼다.

### DNS가 정상이면 웹 사이트도 반드시 정상이다

DNS는 웹 접속 흐름의 첫 부분일 뿐이다. DNS 조회 후에도 포트, 라우팅, [[TCP와 UDP는 무엇이 다를까?|TCP]], TLS, HTTP, 웹 서버 상태를 모두 거쳐야 한다.

## 내가 이해한 방식

DNS는 인터넷 주소 안내소에 가깝다. 주소 안내소는 도착지의 주소를 알려 주지만 그 건물의 문을 열거나 안에서 서비스하는 사람이 일하게 만들지는 않는다.

- DNS는 도메인을 IP로 해석한다.
- 재귀 DNS 리졸버가 루트, TLD, 권한 DNS를 통해 최종 답을 찾는다.
- TTL은 그 답을 얼마나 오래 캐시할지 결정한다.
- DNS 결과가 맞는데 접속이 안 되면 포트, 방화벽, NAT, 서버 설정을 확인한다.
