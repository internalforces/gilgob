## 오늘의 질문

TCP와 UDP는 모두 데이터를 전송하는 프로토콜인데, 왜 두 가지가 필요할까?

> [!question] 핵심질문
> 신뢰성이 필요하면 항상 TCP를 사용하고, 속도가 중요하면 항상 UDP를 사용하면 될까?


## 한 문장으로 이해하기

- **TCP**는 데이터가 순서대로 안전하게 도착하도록 관리하는 **연결 지향 바이트 스트림 프로토콜**이다.
- **UDP**는 각각의 메시지를 독립적으로 전송하는 **비연결형 데이터그램 프로토콜**이다.

## 전송 계층에서의 위치

TCP와 UDP는 모두 [[OSI 7 Layer|OSI 7계층]]의 전송 계층에서 동작한다.

```text
Application Layer
        ↓
Transport Layer
   ├── TCP
   └── UDP
        ↓
Internet Layer
       IP
```

[[IP와 Port|IP와 포트]]가 목적지 컴퓨터와 애플리케이션을 식별한다면, TCP와 UDP는 그 정보를 이용해 데이터를 전달한다.

예:
```text
IP 주소  → 어떤 컴퓨터인가?
Port 번호 → 그 컴퓨터의 어떤 프로그램인가?
```


### TCP의 특징

TCP는 데이터를 보내기 전에 상대방과 연결을 수립한다.
```text
Client                    Server
   │                         │
   │────── SYN ─────────────>│
   │<──── SYN + ACK ─────────│
   │────── ACK ─────────────>│
   │                         │
   │      연결 완료            │
```
이를 [[TCP 3-way handshake|3-way handshake]]라고 한다.

TCP가 제공하는 기능:

- 데이터 전달 확인
- 손실된 데이터 재전송
- 전송 순서 보장
- 중복 데이터 제거
- [[TCP 흐름 제어와 혼잡 제어|흐름 제어]]
- [[TCP 흐름 제어와 혼잡 제어|혼잡 제어]]

> [!note] TCP는 메시지 경계를 보존하지 않는다
> TCP는 데이터를 연속된 바이트 스트림으로 처리한다. 송신자가 두 번 나누어 보냈다고 해서 수신자도 반드시 두 번에 나누어 받는 것은 아니다.


## UDP의 특징

UDP는 별도의 연결 수립 과정 없이 데이터그램을 전송한다.

```text
Client                    Server
   │                         │
   │──── Datagram 1 ────────>│
   │──── Datagram 2 ────X    │
   │──── Datagram 3 ────────>│
```

UDP 자체는 다음을 보장하지 않는다.

- 데이터 도착
- 도착 순서
- 중복 방지
- 재전송
- 혼잡 제어

하지만 TCP보다 구조가 단순하고 메시지 단위를 보존한다.

> [!important] UDP가 무조건 빠른 것은 아니다
> UDP는 연결과 재전송 기능이 적어 지연을 줄이기 쉽지만, 실제 성능은 네트워크 환경과 애플리케이션 구현에 따라 달라진다.

## TCP와 UDP 비교

| 기준     | TCP           | UDP            |
| ------ | ------------- | -------------- |
| 연결 방식  | 연결 지향         | 비연결형           |
| 데이터 형태 | 바이트 스트림       | 데이터그램          |
| 전송 순서  | 보장            | 보장하지 않음        |
| 손실 복구  | 재전송           | 애플리케이션에서 처리    |
| 메시지 경계 | 보존하지 않음       | 보존             |
| 흐름 제어  | 제공            | 제공하지 않음        |
| 혼잡 제어  | 제공            | 제공하지 않음        |
| 헤더 크기  | 상대적으로 큼       | 8바이트           |
| 대표 용도  | 웹, 파일 전송, SSH | 음성·영상, 게임, DNS |

## 사용 사례
### TCP가 적합한 경우
데이터의 정확성과 순서가 중요할 때 사용한다.

- HTTP/1.1
- HTTP/2
- HTTPS
- SSH
- 이메일
- 파일 전송
- 데이터베이스 연결

파일의 일부가 사라지거나 순서가 바뀌면 안 되기 때문이다.

### UDP가 적합한 경우

일부 데이터 손실보다 낮은 지연이 중요할 때 사용한다.

- 실시간 음성 통화
- 영상 스트리밍
- 온라인 게임
- DNS 질의
- 네트워크 상태 탐색

다만 [[DNS는 어떻게 동작할까|DNS]]는 응답 크기나 상황에 따라 TCP를 사용하기도 한다.

[[QUIC과 HTTP3|HTTP/3와 QUIC]]에서 QUIC은 UDP 위에 신뢰성·암호화·혼잡 제어를 구현한다.

## 어떻게 선택할까?

```text
데이터의 정확한 전달이 중요한가?
        │
        ├─ 예 → TCP를 우선 검토
        │
        └─ 아니요
             │
             └─ 낮은 지연과 메시지 단위 전송이 중요한가?
                    │
                    ├─ 예 → UDP를 우선 검토
                    └─ 아니요 → 애플리케이션 요구사항 재검토
```

실제로는 단순히 “신뢰성 대 속도”로만 선택하지 않는다.

다음 조건을 함께 고려해야 한다.

- 데이터 손실을 허용할 수 있는가?
- 순서가 바뀌어도 되는가?
- 실시간성이 중요한가?
- 애플리케이션에서 재전송을 구현할 것인가?
- 연결 이동과 재연결이 자주 발생하는가?

## 내가 이해한 방식

TCP는 택배의 등기 배송과 비슷하다.

- 상대방 확인
- 배송 순서 관리
- 분실 시 재전송
- 도착 여부 확인

UDP는 여러 장의 엽서를 보내는 것과 비슷하다.

- 바로 보낼 수 있음
- 각각의 메시지가 독립적임
- 일부가 사라지거나 순서가 바뀔 수 있음

하지만 UDP 위에서도 애플리케이션이 확인·재전송 기능을 직접 구현할 수 있다.

## 자주 하는 오해

### TCP는 항상 느리다

항상 그런 것은 아니다. TCP는 혼잡 제어와 연결 재사용을 제공하며, 안정적인 대용량 전송에서는 효율적일 수 있다.

### UDP는 데이터가 반드시 손실된다

UDP가 손실을 발생시키는 것은 아니다. 다만 손실이 발생했을 때 UDP 자체가 복구하지 않는다.

### 실시간 서비스는 무조건 UDP다

서비스 요구사항에 따라 TCP나 QUIC을 사용할 수도 있다.
