## 오늘의 질문

TCP는 송신 속도를 조절할 때 수신자의 처리 능력과 네트워크의 수용 능력을 어떻게 함께 고려할까?

> [!question] 핵심질문
> 흐름 제어와 혼잡 제어는 모두 송신량을 제한하는데, 왜 서로 다른 두 가지 제어가 필요할까?

## 한 문장으로 이해하기

**흐름 제어**는 수신 버퍼가 넘치지 않도록 수신자의 여유 공간에 맞춰 보내고, **혼잡 제어**는 네트워크 경로가 과부하되지 않도록 관측된 상태에 맞춰 보내는 TCP의 전송량 조절 기능이다.

## 먼저 차이부터 보기

| 구분 | 흐름 제어 | 혼잡 제어 |
| --- | --- | --- |
| 보호 대상 | 수신 호스트의 버퍼 | 라우터와 네트워크 경로 |
| 판단 기준 | 수신자가 광고한 여유 공간 | ACK, 패킷 손실, RTT, ECN 등의 신호 |
| 주요 변수 | 수신 윈도우 `rwnd` | 혼잡 윈도우 `cwnd`, 임계값 `ssthresh` |
| 주요 기법 | 슬라이딩 윈도우, 윈도우 갱신 | 느린 시작, 혼잡 회피, 빠른 재전송·회복 |
| 해결하려는 문제 | 빠른 송신자가 느린 수신자를 압도하는 문제 | 너무 많은 트래픽이 네트워크를 압도하는 문제 |

둘은 보호 대상이 다르므로 하나가 다른 하나를 대신할 수 없다. 수신자의 버퍼가 충분해도 중간 네트워크가 혼잡할 수 있고, 네트워크가 여유로워도 수신 애플리케이션의 처리 속도가 느릴 수 있다.

## 언제부터 동작할까?

TCP는 [[OSI 7 Layer|OSI 7계층의 전송 계층]]에서 동작한다. 먼저 [[TCP 3-way handshake|3-way handshake]]로 양쪽의 초기 시퀀스 번호를 교환하고 연결을 설정한다. 이후 데이터를 전송하는 동안 ACK와 윈도우 정보를 이용해 흐름 제어와 혼잡 제어를 계속 수행한다.

```text
[[TCP 3-way handshake|연결 설정]]
        ↓
데이터와 ACK 교환
   ├── 수신자 상태 확인: rwnd
   └── 네트워크 상태 추정: cwnd
        ↓
실제 전송량 조절
```

## 흐름 제어

흐름 제어는 **송신자가 수신자의 처리 능력보다 빠르게 데이터를 보내 수신 버퍼가 넘치는 상황을 방지**한다.

### 수신 윈도우 `rwnd`

수신자는 TCP 헤더의 Window 필드를 통해 현재 받을 수 있는 데이터의 크기를 알린다. 이 값이 **수신 윈도우(receive window, `rwnd`)**다.

```text
송신자                                      수신자
   │──── 데이터 ─────────────────────────────>│ 수신 버퍼에 저장
   │<─── ACK, Window=32 KB ──────────────────│ 32 KB 여유
   │──── 최대 32 KB 범위 안에서 전송 ────────>│
```

- 수신 애플리케이션이 데이터를 빠르게 읽으면 버퍼 공간이 늘고 `rwnd`가 커질 수 있다.
- 수신 버퍼의 여유가 줄면 수신자는 더 작은 `rwnd`를 광고한다.
- 버퍼가 가득 차면 `rwnd = 0`을 알려 송신을 일시 중단시킨다.

### 슬라이딩 윈도우

송신자는 세그먼트 하나를 보낼 때마다 ACK를 기다리지 않고 허용된 윈도우 범위 안에서 여러 바이트를 연속으로 보낼 수 있다. ACK가 도착하면 확인된 바이트만큼 윈도우의 시작점이 앞으로 이동한다. 이를 **슬라이딩 윈도우**라고 한다.

```text
보낸 바이트          전송 가능 영역              아직 전송 불가
┌────────────┬────────────────────────┬──────────────────┐
│ ACK 대기 중 │ 현재 윈도우 안의 미전송 바이트 │ 윈도우 바깥 바이트 │
└────────────┴────────────────────────┴──────────────────┘
             ACK 도착 → 윈도우가 오른쪽으로 이동
```

### Zero Window와 윈도우 프로브

`rwnd = 0`이 되면 송신자는 일반 데이터 전송을 멈춘다. 이후 수신자가 보낸 윈도우 갱신 ACK가 손실되면 양쪽이 계속 기다리는 교착 상태가 생길 수 있다.

이를 방지하기 위해 송신자는 **지속 타이머(persist timer)**를 사용해 주기적으로 작은 **윈도우 프로브(window probe)**를 보낸다. 수신자는 현재 윈도우 크기로 응답하고, 윈도우가 다시 열리면 송신을 재개한다.

## 혼잡 제어

혼잡 제어는 **네트워크에 지나치게 많은 데이터가 유입되어 라우터 큐 지연과 패킷 손실이 커지는 상황을 방지**한다.

수신자는 자신의 버퍼 상태를 알 수 있지만, 전체 네트워크 경로의 여유 공간을 직접 알려 주지는 않는다. 따라서 송신자는 ACK 도착 패턴, 패킷 손실, 재전송 타임아웃, RTT 증가, ECN 표시 같은 신호를 이용해 혼잡을 판단한다.

### 혼잡 윈도우 `cwnd`

송신자는 네트워크에 ACK를 받지 않은 채 내보낼 수 있는 데이터의 상한을 **혼잡 윈도우(congestion window, `cwnd`)**로 관리한다.

송신 측에서 ACK를 기다리며 네트워크에 남아 있는 데이터의 양은 기본적으로 다음 두 값 중 작은 값으로 제한된다.

\[
비행\ 중인\ 데이터량 \leq \min(rwnd,\ cwnd)
\]

실제 한 번에 새로 보낼 수 있는 양은 이 한도에서 아직 ACK를 받지 못한 데이터량을 제외하고 계산한다.

### 예시

```text
수신자가 허용한 rwnd = 64 KB
네트워크 상태로 정한 cwnd = 16 KB
→ 최대 16 KB 범위에서 전송

수신자가 허용한 rwnd = 8 KB
네트워크 상태로 정한 cwnd = 32 KB
→ 최대 8 KB 범위에서 전송
```

첫 번째 경우에는 네트워크가 제한 요소이고, 두 번째 경우에는 수신자의 처리 능력이 제한 요소다.

## 대표적인 혼잡 제어 단계

다음 설명은 TCP Reno 계열의 고전적인 동작을 단순화한 것이다. 실제 운영체제는 CUBIC, BBR 등 다른 혼잡 제어 알고리즘을 사용할 수 있으며 세부 동작도 다르다.

### 느린 시작(Slow Start)

연결 초기에는 네트워크가 감당할 수 있는 전송량을 알 수 없으므로 작은 `cwnd`에서 시작한다. 새 데이터에 대한 ACK가 도착할 때마다 `cwnd`를 늘리므로 손실이 없다면 한 RTT마다 대략 두 배로 증가한다.

이름은 느린 시작이지만, 증가 방식은 지수적이므로 실제 증가 속도는 빠르다.

### 혼잡 회피(Congestion Avoidance)

`cwnd`가 느린 시작 임계값인 `ssthresh`에 도달하면 증가 속도를 낮춘다. Reno의 혼잡 회피 단계에서는 한 RTT마다 전체 `cwnd`가 대략 1 MSS씩 증가한다. 이를 **가산 증가(Additive Increase)**라고 한다.

### 빠른 재전송(Fast Retransmit)

수신자는 순서가 어긋난 세그먼트를 받으면 자신이 다음에 기대하는 바이트 번호를 ACK로 반복해서 보낼 수 있다. 송신자가 같은 ACK를 일반적으로 세 번 중복 수신하면 타임아웃을 기다리지 않고 손실로 추정한 세그먼트를 재전송한다.

### 빠른 회복(Fast Recovery)

중복 ACK가 계속 도착한다는 것은 일부 세그먼트가 네트워크를 통과하고 있다는 신호다. Reno는 네트워크 전체가 멈춘 것은 아니라고 보고 `cwnd`를 줄인 뒤 혼잡 회피로 전환한다.

반면 **재전송 타임아웃(RTO)**이 발생하면 더 심한 혼잡으로 판단한다. `ssthresh`를 낮추고 `cwnd`를 작은 값으로 되돌린 뒤 느린 시작을 다시 수행한다.

```text
cwnd
 ↑       느린 시작        혼잡 회피
 │          ╱               ╱
 │        ╱               ╱
 │      ╱               ╱
 │    ╱        손실 → cwnd 감소
 │  ╱
 └────────────────────────────────→ 시간
```

## 두 제어가 함께 작동하는 과정

```text
1. [[TCP 3-way handshake]]로 연결을 설정한다.
2. 수신자는 ACK에 rwnd를 담아 버퍼 여유를 알린다.
3. 송신자는 네트워크 반응을 바탕으로 cwnd를 조절한다.
4. 송신자는 min(rwnd, cwnd) 범위 안에서 데이터를 보낸다.
5. 연결이 유지되는 동안 ACK가 도착할 때마다 이 과정을 반복한다.
```

흐름 제어는 수신자가 명시적으로 광고한 값에 반응한다. 혼잡 제어는 주로 송신자가 네트워크의 반응을 관찰하고 추정한 결과에 반응한다는 점이 핵심 차이다.

## 내가 이해한 방식

물을 보내는 파이프로 비유할 수 있다.

- `rwnd`는 물을 받는 탱크의 남은 공간이다.
- `cwnd`는 중간 파이프가 막히지 않고 전달할 수 있다고 추정한 양이다.
- 송신자는 탱크와 파이프 중 더 작은 한계에 맞춰 물을 보낸다.

탱크가 커도 파이프가 막히면 천천히 보내야 하고, 파이프가 넓어도 탱크가 가득 찼다면 전송을 멈춰야 한다.

## 자주 하는 오해

### 흐름 제어와 혼잡 제어는 같은 기능이다

둘 다 송신량을 조절하지만 보호 대상과 판단 정보가 다르다. 흐름 제어는 수신 호스트를, 혼잡 제어는 네트워크 경로를 보호한다.

### `rwnd`와 `cwnd`는 모두 수신자가 보낸다

`rwnd`는 수신자가 TCP 헤더를 통해 광고한다. `cwnd`는 송신자의 혼잡 제어 알고리즘이 네트워크 상태를 추정해 내부적으로 관리한다.

### 패킷 손실은 항상 혼잡 때문에 발생한다

손실은 무선 오류, 장비 문제 등 다른 원인으로도 발생할 수 있다. 손실 기반 TCP 알고리즘은 원인을 직접 구분하기 어려워 손실을 혼잡 신호로 해석하는 경우가 많다.

### 모든 TCP가 느린 시작과 빠른 회복을 똑같이 구현한다

혼잡 제어 알고리즘과 운영체제 구현에 따라 증가·감소 규칙이 달라진다. Reno의 설명은 핵심 개념을 이해하기 위한 대표적인 모델이다.
